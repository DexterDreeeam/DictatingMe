DictatingMe · 唤醒 E2E 测试计划 计划 / 未实现

四种唤醒模式的可独立运行集成测试：素材下载 → 统一 Setup 输入 → 复刻真实处理流程 → 准确率 / 误识别率量化。

1. 这份计划要解决什么

当前四种唤醒模式（Text / VoiceMatch / SpeakerVerify / Classifier）只有 features.rs 与 scoring/mod.rs 里的少量单元测试，验证的是「函数没写错」，而不是「唤醒词能不能用」。本计划把它升级为可独立运行的端到端集成测试：给定一个唤醒词 + 一组 5 秒音频，跑完真实的 setup 与打分链路，输出准确率与误识别率。

4唤醒模式，同一套输入 Schema
20唤醒词分组（各带 1 个可区分对立词）
280基础素材条数（不含增广）
0提交进 git 的音频字节
可独立运行：不依赖麦克风、不依赖 Tauri、不依赖 UI；只依赖 assets/ 下已下载/已合成的素材，缺素材时测试 skip 而不是 fail。

2. 五个必须回答的问题

#问题用什么指标回答
Q1本人说唤醒词，能唤醒吗TPR / 唤醒率：同一说话人正样本被 EvokeScore.accepted 判定为真的比例
Q2别人说同一个唤醒词，会不会被误唤醒FAR-impostor：非注册说话人正确念出唤醒词时的误接受率（SpeakerVerify 的核心指标）
Q3发音接近但可区分的词会不会误唤醒FAR-confusable：与唤醒词只差一个声母/韵母/声调，或只替换一个音节的短语的误接受率（不含同音同调词）
Q4放着不动，一小时误唤醒几次FA/h：连续噪声与自由语音流上的每小时误唤醒次数
Q5阈值定得对不对ROC / EER：扫描 sensitivity 0.0→1.0，画出 TPR-FAR 曲线并求等错误率

3. 各模式验收基线（首轮建议值，跑完第一轮后按实测回填）

基线不是"必须达到"，而是"低于此值即视为该模式在当前实现下不可用，需要回到算法设计"。所有值在 clean + SNR 20 dB 条件下评估，噪声更强的条件单独记录退化曲线。

一句话目标

让「换个唤醒词好不好用」「这个模式是不是白做的」变成一条命令就能回答的问题。

不在范围内

  • 不测听写（Dictation）识别质量
  • 不测 UI / HUD / 文本注入
  • 不测真实麦克风采集与设备切换
  • 不做模型训练与算法改进（本轮只做度量）

硬约束

  • 素材一律不进 git，只进 assets/ 并被 gitignore
  • 素材可复现：同一 manifest 在任何机器上产出同一批文件
  • 测试可在无素材环境下 skip，不阻塞常规 cargo test

2. 命名约定（二级目录内的文件名即元数据）

测试加载器直接从文件名解析角色，不需要额外的索引文件；manifest 只负责"这个文件从哪来"，文件名负责"这个文件是什么"。

corpus/<group>/<group>_<speaker>_<role>_<style>_<idx>.wav group w01 … w20 唤醒词分组编号 speaker s01 … s08 说话人编号（TTS speaker id 或真人编号） role enroll | pos | imp | cfz 注册 / 正样本 / 冒名者 / 对立词 style normal|loud|soft|fast|slow|far 录制风格，对应 EnrollmentPlan 的 prompt id idx 01 … 同类内序号 例：w01-xiaodi-xiaodi/w01_s03_enroll_normal_01.wav w01-xiaodi-xiaodi/w01_s07_imp_normal_01.wav ← s07 冒名说 w01 的唤醒词 w01-xiaodi-xiaodi/w01_s03_cfz_normal_01.wav ← s03 说对立词「小提小提」(T1)

3. assets-manifest.json 结构

manifest 有两类条目：download（有 URL，可多镜像回退）与 synthesize（无 URL，用本地 TTS 模型按配方生成）。两类都声明 path 与期望校验值，脚本据此做「校验 → 缺失才补」的幂等行为。

与 manifest-cn.json 的分工：两份清单并存，互不合并。
manifest-cn.json 是产品运行时清单——被 tauri.conf.json 打包进安装包、复制到 %LOCALAPPDATA%\DictatingMe\、由 asset_manager.rs 在运行时解析、由 run-package.ps1 硬校验 schemaVersion 1。改它等于改发布链路，与「加一套测试」毫无关系。
assets-manifest.json 是测试语料清单——只被 download-assets.ps1 与测试 harness 读取，产品运行时完全不感知，删掉也不影响应用启动。

为什么是二级

一级回答「这是干什么用的」，二级回答「属于哪一类」。再深一层的信息（说话人 / 角色 / 风格）用文件名承载，遍历成本更低，也便于在资源管理器里肉眼核对。

可删除性分级

  • derived/ reports/：随时可删，脚本秒级重建
  • corpus/ freespeech/：可删，需本地 TTS 重跑（分钟级）
  • models/ noise/：可删，需重新联网下载（GB 级）

体积预估

  • models ≈ 1.3 GB（含 TTS 120 MB）
  • noise ≈ 60 MB
  • corpus 280×5s ≈ 44 MB
  • freespeech ≈ 20 MB
  • derived ≈ 370 MB（可裁剪）

1. 素材从哪来

调研结论：公开的中文唤醒词真人语料要么是数 GB 的整包 tarball、要么需要商业授权，无法按条 HTTP 下载，也无法满足「同一说话人 / 不同说话人」这种 SpeakerVerify 必需的标注维度。因此采用本地多说话人 TTS 合成 + 真实环境噪声增广的方案。

素材类型来源获取方式可复现
唤醒词语音vits-zh-aishell3（174 说话人）下载 TTS 模型后本地合成，speaker/语速/文本全可控完全
环境噪声MS-SNSD（微软开源）按 commit 固定的 raw URL 逐文件下载，30 条完全
自由语音流同 TTS 模型 + 公开中文句表本地合成后拼接成 8–10 分钟长音频完全
对立词语音同 TTS 模型每组人工指定一个可区分对立词（T1–T4），与唤醒词同 speaker 一起合成完全
真人录音（可选）本人 / 同事后续可放进同样的目录结构，覆盖同名合成素材，测试代码不用改手工
合成素材的定位：它保证的是相对比较有效——模式之间、阈值之间、噪声条件之间的排序可信。绝对数值仍需少量真人录音校准，这一步放在 M6。

3. 20 个唤醒词分组

分组要覆盖不同音节数、不同声调组合、叠词与非叠词、含英文字母的混合词——这些都会显著影响 KWS 与模板匹配的表现。每组指定一个对立词作为负样本。

硬性规则：对立词禁止同音同调。「小迪 / 小笛」（都是 xiǎo dí）、「记录 / 记路」（都是 jì lù）、「记下来 / 寄下来」（都是 jì xià lái）这类词，人耳和模型都不可能区分，测出来的 FAR 只是噪声。对立词必须在声母、韵母、声调或整个音节上至少有一处真实差异。
对立类型定义难度与意义
T1 声母韵母与声调完全相同，只差一个声母（d/t、b/p、z/zh、n/l、d/y）最难的可区分档；考察模型对送气/不送气、平翘舌的分辨力
T2 韵母对应音节的韵母不同（可伴随声调差异），词形高度相似次难；噪声下最先失效的一类
T3 声调音节完全相同，只有声调不同中文特有；纯声学模板（VoiceMatch）对声调不敏感，是它的弱项
T4 音节替换整词中有一个音节完全不同，且对立词是日常真实用语最容易区分，但最贴近真实误触发场景——用户本来就在说这句话
T0 同音同音同调已排除，不测

类型分布组数报告要求
T1 声母3（w01 w10 w11）FAR 最高属预期；若 T1 的 FAR 与 T4 相当，说明模型根本没在做音素级判别
T2 韵母5（w06 w15 w16 w17 w19）与 SNR 联动观察：韵母差异在 10 dB 以下最先被噪声抹平
T3 声调5（w03 w04 w08 w14 w18）VoiceMatch 预计在这一类上明显劣于 Text（DTW 对基频不敏感），这是区分两个模式价值的关键证据
T4 音节替换7（w02 w05 w07 w09 w12 w13 w20）FAR 应显著低于 T1/T2；若不低，说明唤醒判定基本没有内容分辨力，只是在做「有没有人说话」

4. 说话人分配

角色说话人规则
owner（注册者）每组 1 位，20 组轮转使用 s01–s08enroll 与 pos 用同一位；enroll 与 pos 的合成参数（语速/停顿）不同，避免"注册即测试"的自证
impostor（冒名者）每组 2 位，与 owner 性别各异其一同性别 impostor 是难例，异性别是易例，分开统计
freespeech4 位，与上面不重叠保证 FA/h 长跑不会碰巧命中注册说话人
已知局限：TTS 同一 speaker id 的声纹一致性高于真人多次录音，SpeakerVerify 的 TPR 会偏乐观、FAR-impostor 会偏乐观。计划用「加噪 + 变速 + 增益扰动」人为拉开注册与测试的分布差，并在报告里标注该偏差。

为什么必须 TTS

SpeakerVerify 要回答的问题是"别人说同一句话会不会过"。这要求同一文本、不同说话人的成对素材——真实公开数据集几乎没有这种标注，TTS 是唯一能低成本拿到 20 组 × 3 说话人成对样本的手段。

合成参数固定项

  • 采样率 16 kHz、单声道、16 bit
  • 统一补静音至 5000 ms，对齐 EnrollmentPlan.recording_duration_ms
  • 唤醒词位置随机落在 1.0–2.5 s，避免模型学到"开头即唤醒词"

对立词怎么选

先写拼音（含声调）逐音节对照，只有至少一处声母/韵母/声调不同才收录，同音同调一律作废。合成后必须人耳抽听确认两条音频真的听得出区别——TTS 对同音字输出的是同一段波形，混进去等于往数据集里塞噪声。

为什么要分 T1–T4

把「声母对立」和「换一个音节」混在一起算平均 FAR，得到的数字既不能说明模型好也不能说明模型差。分档后才能回答真正有用的问题：模型是做到了音素级判别，还是只在做「有没有人说话」。

许可

MS-SNSD 噪声为 CC0 / CC BY-SA 3.0；aishell3 与 vits 模型遵循各自 Apache-2.0 / CC BY-SA 许可。素材不入库，仅本地生成，README 中保留出处说明。

为什么分 A/B 两阶段

Setup 与 Detect 的失败原因完全不同：前者是素材/门禁/训练问题，后者是阈值/特征/噪声问题。分开断言才能在报告里直接定位。

KWS 命中信号怎么来

四个模式的 overall 都依赖 phrase_score。测试用 keyword_syntax_for_model() 生成关键词后，跑真实 KWS 流拿命中时刻，而不是硬编码 keyword_hit=true——否则 Text 模式等于没测。

耗时预估

  • Text ≈ 1 min
  • VoiceMatch ≈ 2 min
  • SpeakerVerify ≈ 4 min（含声纹推理）
  • Classifier ≈ 6 min（含训练）
  • FA/h 长跑 ≈ 3 min

1. 条件维度

维度取值为什么要测
语速0.9x / 1.0x / 1.1xDTW 模板对时长敏感；resample_sequence 归一化到 64 帧后是否还稳
信噪比clean / 20 dB / 10 dB / 5 dBClassifier 的负样本就是噪声，必须验证它没有把"有噪声"学成"不是唤醒词"
噪声类别crowd / traffic / office / machinery / home人声类噪声（babble）对声纹与 KWS 的干扰远大于稳态噪声
增益-6 dB / 0 dB / +6 dB（+6 触发轻微削波）验证 recording_quality() 的 rms / clipping 门禁是否合理
灵敏度0.0 → 1.0 步进 0.05出 ROC 曲线与 EER，回答"默认 0.65 是不是好值"
组合爆炸控制：全笛卡尔积是 3×4×5×3 = 180 种条件 × 4 模式 × 20 组 × 14 条 ≈ 20 万次推理，不可接受。采用分层抽样：核心条件全跑，边缘条件按组抽样。

T1/T2 与 T3/T4 分列是硬性要求：合并成单一 FAR-cfz 会让 T4 的 0.05 把 T1 的 0.29 拉平到 0.15 左右，看上去「没问题」，实际上模型在最难的声母对立上已经一半失守。

样本量够不够

L1 每个 (mode×condition) 有 80 个正样本、40 个 impostor。TPR 0.9 时 95% 置信区间约 ±0.07，足够做"能不能用"的判断，不足以做"0.90 vs 0.92 谁更好"的比较。

失败即数据

L3/L5 允许 FAIL。目标不是全绿，而是拿到退化曲线：知道 SNR 降到多少、语速偏到多少就不能用了。

回归对比

每次运行与 reports/history/ 最近一次对比，任一 (mode×L1条件) 的 TPR 下降超过 0.05 或 FAR 上升超过 0.05 即标红。

4. 结论

#结论依据
1 KWS 是整条链路的天花板，也是当前最大短板。 四种模式的 TPR 都被 KWS 检出率封顶在 63.6%，即使干净语音也有 36% 漏唤醒。 text 模式 = 纯 KWS，TPR 63.6%；其余模式只能更低。KWS 探针显示分组检出率 0%（嗨小迪）～100%（帮我打字），音色间 18%～93%。
2 漏唤醒是「说什么 + 谁在说」决定的，不是环境决定的。 噪声、语速、音量对 KWS 几乎没有影响。 text 模式在 traffic@5 dB 下 TPR 仍是 65.0%，与 clean 的 63.7% 持平。
3 text 模式不具备防冒充能力，任何人念出唤醒词都会触发，只适合单人独占场景。 冒充者 FAR 67.5%——等于冒充者只要过了 KWS 就一定唤醒。
4 speakerVerify 是四者里唯一「不牺牲 TPR 换安全」的模式。 相对 text 只掉 1.1 个点 TPR，却把冒充者 FAR 从 67.5% 压到 10%，且完全不受噪声影响。 TPR 62.5% vs 63.6%；traffic@5 dB 下 TPR 65.0%（campplus 声纹嵌入对噪声鲁棒）。
5 voiceMatch 的 DTW 模板匹配对噪声极度脆弱，安静环境可用，嘈杂环境基本失效。 但它的冒充者拒绝率是四者最好的。 TPR 63.7%（clean）→ 12.5%（crowd@10 dB）→ 1.2%（traffic@5 dB）；冒充者 FAR 2.5%。
6 classifier 模式全面劣于其它三种：TPR 最低、抗噪最差、防冒充也只是中等。 6 条正样本 + 噪声负样本训练出的逻辑回归泛化不足。 TPR 37.9%，crowd@10 dB 下归零，冒充者 FAR 仍有 32.5%。
7 近音词误唤醒完全由 KWS 决定，四种模式无差别。 因为对立词是本人说的，声纹/模板/分类器都判它是「对的人」，只剩短语这一道闸。 其中只差声母（T1 33.3%）或只差声调（T3 30.0%）挡不住， 差韵母（T2 0%）或差整个音节（T4 7.1%）才安全。 T1/T2/T3/T4 的 FAR 在四种模式下数值完全一致。
8 无关语音不会误唤醒。45 条自由语音在四种模式下 FAR 全为 0。 freeSpeech 60 次判定，0 次唤醒。

5. 由数据得出的行动项

优先级行动预期收益
P0调 KWS 触发阈值 / 引入 sherpa 的 keyword boosting score，或换更大的 KWS 模型。 当前 sensitivity_to_threshold(0.65) = 0.308 且未设 :score 提升值。 直接抬高全部四种模式的 TPR 天花板
P0唤醒词设置页在用户输入短语后，用实录样本实测检出率并给出提示—— 现在用户完全可能选到一个 0% 检出的短语（如「嗨小迪」）。 规避最差情况
P1把 speakerVerify 设为推荐默认模式，voiceMatch 降级为「安静环境」选项。 同等 TPR 下 FAR 从 23.6% 降到 7.1%
P1对 voiceMatch / classifier 的特征做噪声归一（CMVN 或谱减）， 现在 extract_feature_sequence 直接用原始对数频带能量。 修复噪声下 TPR 归零
P2重新评估 classifier 模式是否值得保留。 各项指标均被其它模式支配
P2唤醒词校验时警告「与常见词只差声母或声调」的短语。 降低 T1/T3 类误唤醒

6. 复现方式

cargo run -p xtask --release -- corpus          # 合成 325 条语料
cargo test --release -p dictatingme-runtime --test evoke_e2e -- --ignored --nocapture
