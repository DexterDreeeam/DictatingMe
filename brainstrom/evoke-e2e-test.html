DictatingMe · 唤醒 E2E 测试计划 计划 / 未实现

四种唤醒模式的可独立运行集成测试：素材下载 → 统一 Setup 输入 → 复刻真实处理流程 → 准确率 / 误识别率量化。

1. 这份计划要解决什么

当前四种唤醒模式（Text / VoiceMatch / SpeakerVerify / Classifier）只有 features.rs 与 scoring/mod.rs 里的少量单元测试，验证的是「函数没写错」，而不是「唤醒词能不能用」。本计划把它升级为可独立运行的端到端集成测试：给定一个唤醒词 + 一组 5 秒音频，跑完真实的 setup 与打分链路，输出准确率与误识别率。

4唤醒模式，同一套输入 Schema
20唤醒词分组（各带 1 个可区分对立词）
280基础素材条数（不含增广）
0提交进 git 的音频字节
可独立运行：不依赖麦克风、不依赖 Tauri、不依赖 UI；只依赖 assets/ 下已下载/已合成的素材，缺素材时测试 skip 而不是 fail。

2. 五个必须回答的问题

#问题用什么指标回答
Q1本人说唤醒词，能唤醒吗TPR / 唤醒率：同一说话人正样本被 EvokeScore.accepted 判定为真的比例
Q2别人说同一个唤醒词，会不会被误唤醒FAR-impostor：非注册说话人正确念出唤醒词时的误接受率（SpeakerVerify 的核心指标）
Q3发音接近但可区分的词会不会误唤醒FAR-confusable：与唤醒词只差一个声母/韵母/声调，或只替换一个音节的短语的误接受率（不含同音同调词）
Q4放着不动，一小时误唤醒几次FA/h：连续噪声与自由语音流上的每小时误唤醒次数
Q5阈值定得对不对ROC / EER：扫描 sensitivity 0.0→1.0，画出 TPR-FAR 曲线并求等错误率

3. assets-manifest.json 结构

manifest 有两类条目：download（有 URL，可多镜像回退）与 synthesize（无 URL，用本地 TTS 模型按配方生成）。两类都声明 path 与期望校验值，脚本据此做「校验 → 缺失才补」的幂等行为。

与 manifest-cn.json 的分工：两份清单并存，互不合并。
manifest-cn.json 是产品运行时清单——被 tauri.conf.json 打包进安装包、复制到 %LOCALAPPDATA%\DictatingMe\、由 asset_manager.rs 在运行时解析、由 run-package.ps1 硬校验 schemaVersion 1。改它等于改发布链路，与「加一套测试」毫无关系。
assets-manifest.json 是测试语料清单——只被 download-assets.ps1 与测试 harness 读取，产品运行时完全不感知，删掉也不影响应用启动。

为什么是二级

一级回答「这是干什么用的」，二级回答「属于哪一类」。再深一层的信息（说话人 / 角色 / 风格）用文件名承载，遍历成本更低，也便于在资源管理器里肉眼核对。

可删除性分级

  • derived/ reports/：随时可删，脚本秒级重建
  • corpus/ freespeech/：可删，需本地 TTS 重跑（分钟级）
  • models/ noise/：可删，需重新联网下载（GB 级）

体积预估

  • models ≈ 1.3 GB（含 TTS 120 MB）
  • noise ≈ 60 MB
  • corpus 280×5s ≈ 44 MB
  • freespeech ≈ 20 MB
  • derived ≈ 370 MB（可裁剪）

1. 素材从哪来

调研结论：公开的中文唤醒词真人语料要么是数 GB 的整包 tarball、要么需要商业授权，无法按条 HTTP 下载，也无法满足「同一说话人 / 不同说话人」这种 SpeakerVerify 必需的标注维度。因此采用本地多说话人 TTS 合成 + 真实环境噪声增广的方案。

素材类型来源获取方式可复现
唤醒词语音vits-zh-aishell3（174 说话人）下载 TTS 模型后本地合成，speaker/语速/文本全可控完全
环境噪声MS-SNSD（微软开源）按 commit 固定的 raw URL 逐文件下载，30 条完全
自由语音流同 TTS 模型 + 公开中文句表本地合成后拼接成 8–10 分钟长音频完全
对立词语音同 TTS 模型每组人工指定一个可区分对立词（T1–T4），与唤醒词同 speaker 一起合成完全
真人录音（可选）本人 / 同事后续可放进同样的目录结构，覆盖同名合成素材，测试代码不用改手工
合成素材的定位：它保证的是相对比较有效——模式之间、阈值之间、噪声条件之间的排序可信。绝对数值仍需少量真人录音校准，这一步放在 M6。

3. 20 个唤醒词分组

分组要覆盖不同音节数、不同声调组合、叠词与非叠词、含英文字母的混合词——这些都会显著影响 KWS 与模板匹配的表现。每组指定一个对立词作为负样本。

硬性规则：对立词禁止同音同调。「小迪 / 小笛」（都是 xiǎo dí）、「记录 / 记路」（都是 jì lù）、「记下来 / 寄下来」（都是 jì xià lái）这类词，人耳和模型都不可能区分，测出来的 FAR 只是噪声。对立词必须在声母、韵母、声调或整个音节上至少有一处真实差异。
对立类型定义难度与意义
T1 声母韵母与声调完全相同，只差一个声母（d/t、b/p、z/zh、n/l、d/y）最难的可区分档；考察模型对送气/不送气、平翘舌的分辨力
T2 韵母对应音节的韵母不同（可伴随声调差异），词形高度相似次难；噪声下最先失效的一类
T3 声调音节完全相同，只有声调不同中文特有；纯声学模板（VoiceMatch）对声调不敏感，是它的弱项
T4 音节替换整词中有一个音节完全不同，且对立词是日常真实用语最容易区分，但最贴近真实误触发场景——用户本来就在说这句话

角色说话人规则

已知局限：TTS 同一 speaker id 的声纹一致性高于真人多次录音，SpeakerVerify 的 TPR 会偏乐观、FAR-impostor 会偏乐观。计划用「加噪 + 变速 + 增益扰动」人为拉开注册与测试的分布差，并在报告里标注该偏差。

为什么必须 TTS

SpeakerVerify 要回答的问题是"别人说同一句话会不会过"。这要求同一文本、不同说话人的成对素材——真实公开数据集几乎没有这种标注，TTS 是唯一能低成本拿到 20 组 × 3 说话人成对样本的手段。

合成参数固定项

  • 采样率 16 kHz、单声道、16 bit
  • 统一补静音至 5000 ms，对齐 EnrollmentPlan.recording_duration_ms
  • 唤醒词位置随机落在 1.0–2.5 s，避免模型学到"开头即唤醒词"

对立词怎么选

先写拼音（含声调）逐音节对照，只有至少一处声母/韵母/声调不同才收录，同音同调一律作废。合成后必须人耳抽听确认两条音频真的听得出区别——TTS 对同音字输出的是同一段波形，混进去等于往数据集里塞噪声。

为什么要分 T1–T4

把「声母对立」和「换一个音节」混在一起算平均 FAR，得到的数字既不能说明模型好也不能说明模型差。分档后才能回答真正有用的问题：模型是做到了音素级判别，还是只在做「有没有人说话」。

为什么分 A/B 两阶段

Setup 与 Detect 的失败原因完全不同：前者是素材/门禁/训练问题，后者是阈值/特征/噪声问题。分开断言才能在报告里直接定位。

KWS 命中信号怎么来

四个模式的 overall 都依赖 phrase_score。测试用 keyword_syntax_for_model() 生成关键词后，跑真实 KWS 流拿命中时刻，而不是硬编码 keyword_hit=true——否则 Text 模式等于没测。

样本量够不够

L1 每个 (mode×condition) 有 80 个正样本、40 个 impostor。TPR 0.9 时 95% 置信区间约 ±0.07，足够做"能不能用"的判断，不足以做"0.90 vs 0.92 谁更好"的比较。

失败即数据

L3/L5 允许 FAIL。目标不是全绿，而是拿到退化曲线：知道 SNR 降到多少、语速偏到多少就不能用了。

回归对比

每次运行与 reports/history/ 最近一次对比，任一 (mode×L1条件) 的 TPR 下降超过 0.05 或 FAR 上升超过 0.05 即标红。

6. 结论

#结论依据
1 KWS 是整条链路的天花板，也是当前最大短板。 四种模式的 TPR 都被 KWS 检出率封顶在 63.6%，即使干净语音也有 36% 漏唤醒。 text 模式 = 纯 KWS，TPR 63.6%；其余模式只能更低。KWS 探针显示分组检出率 0%（嗨小迪）～100%（帮我打字），音色间 18%～93%。
2 漏唤醒是「说什么 + 谁在说」决定的，不是环境决定的。 噪声、语速、音量对 KWS 几乎没有影响。 text 模式在 traffic@5 dB 下 TPR 仍是 65.0%，与 clean 的 63.7% 持平。
3 text 模式不具备防冒充能力，任何人念出唤醒词都会触发，只适合单人独占场景。 冒充者 FAR 67.5%——等于冒充者只要过了 KWS 就一定唤醒。
4 speakerVerify 在不损失 TPR 的前提下拿到了防冒充能力。 它与 text 的 TPR 在统计上没有差别（62.5% vs 63.6%，置信区间高度重叠）， 却把冒充者 FAR 从 67.5% 压到 10%，且完全不受噪声影响。 TPR 62.5% [58.4, 66.4] vs text 63.6% [59.5, 67.5]； traffic@5 dB 下 TPR 65.0%（campplus 声纹嵌入对噪声鲁棒）。
5 voiceMatch 的 DTW 模板匹配对噪声极度脆弱，安静环境可用，嘈杂环境基本失效。 它的冒充者 FAR 数字最低，但与 speakerVerify 在统计上不可区分（n = 40 太小）， 不能据此认为它更安全。 TPR 63.7%（clean）→ 12.5%（crowd@10 dB）→ 1.2%（traffic@5 dB），跨度 62 点， 远超 ±10 点噪声；冒充者 FAR 2.5% [0.4, 12.9] vs speakerVerify 10% [4.0, 23.1]。
6 classifier 模式全面劣于其它三种：TPR 最低、抗噪最差、防冒充也只是中等。 6 条正样本 + 噪声负样本训练出的逻辑回归泛化不足。 TPR 37.9%，crowd@10 dB 下归零，冒充者 FAR 仍有 32.5%。
7 近音词误唤醒完全由 KWS 决定，四种模式无差别，且整体不达标。 因为对立词是本人说的，声纹/模板/分类器都判它是「对的人」，只剩短语这一道闸。 合计 FAR 17.5% [8.8, 31.9]，区间下界已高于 5% 目标。
注：T1/T2/T3/T4 四档之间的排序不可信——每档只有 6～14 条， 置信区间跨度超过 20 个点，互相完全重叠。目前只有「T3 声调档不达标」一条撑得住。 要判断「哪种近音差异最危险」，每档需要 ≥ 100 条。		 T1/T2/T3/T4 的 FAR 在四种模式下数值完全一致，证明判别只发生在 KWS。
8 没有观察到高频误唤醒，但远未验证达标。 45 条自由语音、60 次判定、共约 5 分钟音频，四种模式 0 次误唤醒。 这只能排除「每小时几十次」那种量级的问题， 距离 ≤ 0.5 次/小时的目标还差两个数量级的样本量。 0/60，95% 上界 6.0%，换算约 ≤ 43 次/小时。验证 0.5 次/小时需 4～6 小时连续语音。

一句话结论

四种模式全部卡在同一个瓶颈上：KWS 召回率 63.6%。 后面三种模式的 TPR 都是「KWS 召回 × 本级通过率」， 所以第一级不抬起来，改后面几级没有意义。

唯一统计上确认的缺陷

  • 整体 TPR 远低于 90% 目标
  • T3（声调差异）档不达标
  • 自由语音误唤醒上界 ≈ 43 次/小时，目标 0.5

不要过度解读

语料是 TTS 合成而非真人录音，绝对值不能外推到线上。 可靠的是横向比较与瓶颈定位。

1. 为什么必须先修 text 模式

scoring/mod.rs:122 里 text 的 overall = phrase_score × 0.82 + voice_activity × 0.18， 而 evaluate_candidate() 把 phrase_score 直接钉成 1.0，所以 overall 恒 ≥ 0.82； 敏感度 0.65 时门限只有 0.464。0.82 永远大于 0.464 —— text 模式一旦 KWS 命中就必然唤醒。 于是 text 的 TPR 与 KWS 召回一比一相等，一个百分点都不差。

另外三种模式的 overall = phrase_score.min(mode_score)，也就是先过 KWS 才轮到自己。 所以 KWS 召回是四种模式共同的天花板， voiceMatch 实测 43.2% ≈ 63.6%（KWS）× 68%（DTW），完全对得上。

结论：「提高 text 模式 TPR」这个问题，等价于「提高 KWS 召回率」。 而提高 KWS 召回，同时把另外三种模式的天花板一起抬起来。

5. 多变体注册：唯一免费的那条规则

为了消掉选择偏差，这一轮改成在看结果之前就把规则定死， 规则只看唤醒词的字面形态、不看任何检出数据。 注册方式是 sherpa 的多行关键词 + 共享同一个 @alias， 命中任意一行都算命中同一个唤醒词（process_frame 比的正是 alias）。 全部跑在 max_active_paths = 8 之上，回答的是「beam 已经放宽之后还有没有增量收益」。

先把「超集触发」的语义说清楚，因为它决定了怎么算误触发：
注册了 小迪 → 用户说「小迪小迪」会触发。这是预期行为，不算误触发。
只注册 小迪小迪 → 用户说「小迪」不会触发。这也是预期行为。
换句话说，多注册一个短变体，等于把唤醒词整体放宽成那个短变体—— 注册 小迪 之后，唤醒词事实上就是「小迪」，而不再是「小迪小迪」。 这是这条方案真正的产品含义，也是它的全部风险来源。

「首二字 / 末二字」那个 90% 识别率 + 10% 误触发率，是本页最危险的一组数字。 它同时看起来识别率最高、误触发率最低——比什么都不改还低。这不可能是真的。

数字是怎么变好看的：这条规则给「开始听写」额外注册了 开始。 于是对立词「开始停歇」触发了——但按上面的语义， 它包含已注册的 开始，所以算预期行为、要豁免。 实测 13/20 组的对立词都属于这种情况，30 条命中里 24 条被豁免， 误触发率就从 34% 掉到了 10%。豁免本身没错，错在它掩盖了真实代价。

真实代价在哪：注册 开始 之后，你的唤醒词事实上就是「开始」两个字。 这条规则在 20 组里派生出的是 开始、打开、记录、输入、 说话、听写、帮我、快来 这一类词—— 全是日常对话里的高频词。代价不会出现在对立词上（被豁免了）， 只会出现在你正常说话的时候。

而这恰恰是我测不到的：自由语音语料只有 15 句独立文本， 其中包含上述任一变体的正好是 0 句。 所以那个「日常说话 6.7%，一条没变」不是证据，是语料没覆盖到。 要给这条规则下结论，需要几百句真实日常对话语料，本轮没有。 在补上之前，不要采纳这条规则。

对比之下，「AABB 前半」派生出的是 小迪、小助、 小贝、小七 这类「小X」结构，本身就不是日常用语， 撞车概率低得多。这是它免费的真正原因，不是运气。 顺带一个语料里的实例：自由语音「接下来我会把重点放在性能优化…」 包含 下来——而 下来 正是 w06「记下来」的一个候选子词。 通用子词的风险长这样。

「去尾一字」则是纯亏：识别率一点没涨（81.2%），对立词却从 35% 冲到 62.5%。 因为「开始听」这种残词既不像完整词那么好检，又比全词松，两头不讨好，直接排除。

w05「嗨小迪」和 w07「语音输入」四条规则全部救不回来 （0/4 → 0/4，「语音输入」在最激进规则下也只到 2/4）。 这两个词是模型层面的硬失败，任何参数和注册技巧都无效， 只能靠 setup 阶段试检出、劝退用户换词。 当前 86.2% 与 90% 目标之间的缺口，主要就是这两个词。

7. voiceMatch 根因：绝对 RMS 门限在噪声下毁掉时间对齐

voiceMatch 的 TPR = KWS 召回 × DTW 通过率。实测 clean 下 DTW 通过率约 100% （所以 clean 的 voiceMatch TPR 与 text 相同），traffic@5dB 下掉到 ~1%。 问题 100% 在噪声鲁棒性，与干净精度无关。

features.rs:153 有一句 if rms >= 0.003：低于这个能量的帧直接丢弃。 这是个写死的绝对门限。干净音频里静音帧被丢掉，序列只剩语音帧； 一旦加噪，噪声把每一帧的 RMS 都抬过门限，于是整段 5 秒全部保留。 紧接着 resample_sequence(.., 64) 把序列线性压回固定 64 帧—— 干净样本的 64 帧几乎全是关键词，加噪样本的 64 帧里关键词只占一小段。 时间对齐在进 DTW 之前就已经被改写了。

自由语音语料太薄
15 句独立文本 / 60 次判定		 这是本轮最大的一个缺口。「注册通用子词」的全部风险都落在这一项上， 而现有语料里恰好没有一句包含 开始/打开/记录， 所以「6.7% 一条没变」不是证据，是测不到。 要给通用子词方案下结论，需要几百句日常对话。
AABB 规则的收益 n 太小 +5.0 点 TPR 全部来自 w01 一组的 4 条样本翻转，p=0.125。 代价实测为零且机制上单调，所以可以采纳， 但不要把 86.2% 当成一个稳定的期望值。
num_trailing_blanks 没扫 它控制关键词后需要多少静音才判定成立，理论上是 FAR 的直接旋钮。 本轮固定在默认值。
B/C 只在离线特征层验证 还没接进 5.2 秒滚动打分窗口跑端到端， 实际收益可能与离线数字有出入。
B/C 的参数是拍脑袋的 20 分位当底噪、35% 插值点、1.6 秒裁剪窗—— 这三个数都没做敏感性扫描，可能还有余量。
speakerVerify / classifier 未展开 按要求先做前两种。但第 1 条改动（beam 宽度）对它们同样有效， 因为 KWS 是所有模式的第一级。
语料仍是 TTS 合成 所有绝对值都不能外推到真人。可靠的是各方案之间的相对排序， 因为它们跑在完全相同的样本上。

只看两个数

识别率 68.8% → 86.2%
误触发率 12% → 18%
改两处：beam 宽度 4→8，AABB 词加注前半。 多出来的误触发全在「刻意念近音词」上， 日常说话误唤醒 6.7% 一条没变。

最大的一条

max_active_paths 一行改动，识别率 68.8 → 81.2%， 日常说话误唤醒不变，CPU 涨不到 22%。 四种模式共享这个收益，因为 KWS 是所有模式的第一级。

第二条（免费）

AABB 重复型唤醒词额外注册前半（小迪小迪 加注 小迪）， 再 +5.0 点到 86.2%，对立词与日常说话各 0 条变化。

被实验推翻的直觉

  • keywords_threshold 是空操作
  • CMVN 是负收益
  • 增广注册阈值只是放水，冒充误接受 5% → 40%
  • paths=16 比 8 好看，但 p=0.125，是噪声
  • 「去尾一字」子词 0 收益、对立词翻倍

指标会骗人的地方

注册 开始、打开 这类通用子词， 误触发率会因「超集豁免」而看起来降到 10%，比不改还低。 但真实代价挪到了「你正常说话」上——而 15 句语料测不到。 别被那个 90% / 10% 骗了。

为什么用 McNemar

所有对比跑在同一批样本上，属于配对数据。 直接比两个独立置信区间会低估显著性—— paths 4→8 的区间是重叠的，但配对看是净 10 中、0 丢，p≈0.002。

最深的坑

voiceMatch 在噪声下即使修好时间对齐也只有 11% 通过率。 12 维对数带能量、无 mel/DCT/delta 的特征， 低信噪比下判别力接近于零。这不是调参能解决的。

等你拍板

voiceMatch 该不该负责拒绝他人？ 既然已有独立的 speakerVerify 模式， 如果答案是「不该」，方案 A 就从陷阱变成合理选择，TPR 可到 71.9%。
